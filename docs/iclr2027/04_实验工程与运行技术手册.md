# 实验工程与运行技术手册

## 1. 文档目的

本文汇总本工作空间中已经验证有效的实验工程经验，供后续迁移到其他项目或计算节点时复用。内容侧重运行可靠性、GPU利用、评估加速、结果可比性和实验审计，不重复具体模型结论。

核心原则是：**先保证实验协议等价和结果可追溯，再并行加速；训练、Repair、蒸馏和评估必须分阶段记录。**

---

## 2. 推荐的实验目录约定

每个实验使用独立目录，至少保留：

```text
logs/<task>/<experiment>/
├── STATUS
├── train.log
├── model/
│   ├── eval_best_flow.pth
│   ├── structure_best_flow.pth
│   └── checkpoints/
├── eval120/
│   ├── metrics.json
│   ├── trajectories.npz
│   └── trajectory_comparison.png
└── eval480/
    ├── metrics.json
    ├── trajectories.npz
    └── trajectory_comparison.png
```

约定：

- `STATUS`写入`TRAINING`、`EVALUATING`、`COMPLETE`或`FAILED`及时间戳，便于不读取长日志就判断状态；
- 标准输出和错误输出重定向到阶段日志，不依赖终端滚屏；
- 不覆盖旧实验目录；方法、结构、seed和训练预算应体现在目录名或元数据中；
- checkpoint、数据集和大规模轨迹文件不提交Git，只提交代码、配置、指标摘要和必要图片；
- 从其他工作空间复用脚本时，先将脚本中的项目绝对路径、Python解释器和bundle路径参数化。

## 3. GPU资源验收与任务映射

### 3.1 启动前必须检查

```bash
nvidia-smi --query-gpu=index,name,memory.total,memory.used,utilization.gpu \
  --format=csv
echo "$CUDA_VISIBLE_DEVICES"
```

同时检查调度作业、剩余时限和实际可见GPU。不要根据“申请了几张卡”推断程序内一定可见相同数量。

多卡启动脚本应在开头：

1. 统计可见GPU数量；
2. 数量不足时写入`STATUS`并退出；
3. 明确记录每张GPU对应的方法；
4. 等待全部子进程并汇总退出码，任一失败则整组标记失败。

本项目中有效的模式是“一张GPU对应一个实验臂”，例如四个损失消融分别绑定GPU 0–3。这样比单个小模型做数据并行更适合独立消融，也避免通信开销。

### 3.2 显存利用率低不等于模型计算慢

机器人闭环评估通常受环境仿真、Python控制循环和CPU单线程限制。单进程即使只占少量显存，也不能通过单纯增大batch获得同等结果，因为每条轨迹存在时序依赖。

有效方案是：

- 训练：不同实验臂分配不同GPU；
- 闭环评估：每个模型占一张GPU，在该GPU上启动多个独立环境进程；
- 长评估：按episode区间分片，完成后确定性合并。

## 4. 单GPU四进程评估

### 4.1 已验证方案

当前Avoiding评估默认采用：

> 每个模型单GPU，每GPU四个独立worker，按episode区间分片。

对应入口：

```bash
scripts/run_deployed_flow_parallel_eval.sh \
  GPU MODEL_DIR OUTPUT_DIR \
  N_TRAJECTORIES EPISODE_START SEED \
  4 STEPS LAYERS EMBED_DIM HEADS
```

例如Standard-120：

```bash
scripts/run_deployed_flow_parallel_eval.sh \
  0 path/to/model path/to/eval120 \
  120 0 42 4 16 3 48 3
```

脚本将120条轨迹拆为四个连续且不重叠的episode区间，每个worker使用同一个模型、seed基准和GPU，最后由
`scripts/merge_deployed_flow_eval_shards.py`合并。

### 4.2 为什么能够保持原协议精度

评估随机性必须由`seed + 全局episode index`决定，而不能由worker本地序号决定。满足这一点时，分片只是改变执行顺序，不改变每条轨迹的初始状态和噪声。

合并时必须：

- 保留全部轨迹、success标记和mode编码；
- 按全局episode顺序拼接，尤其是paired评估；
- 从合并后的原始样本重新计算SR、覆盖和熵；
- 不能对各worker的熵或覆盖做算术平均。

本工作空间已对单进程与四worker结果做过逐轨迹等价性验证，因此后续Standard-120/480可以默认使用四worker。但迁移到新任务或新评估器时，必须重新做一次等价性验收。

### 4.3 新环境的等价性验收

先用固定checkpoint、seed和较小样本数分别运行单worker与四worker：

```text
single: workers=1, episodes=0...N-1
multi:  workers=4, episodes=0...N-1
```

比较：

- success数组完全一致；
- mode数组完全一致；
- 每条轨迹长度和坐标一致或满足预设浮点容差；
- 合并后SR、覆盖、熵一致。

只有通过后，才能将多worker结果用于正式表格。

### 4.4 worker数量不要盲目增加

四worker是当前节点、环境和模型上的经验甜点，不是普适常数。继续增加进程可能遇到：

- CPU核争用；
- 仿真器或图形后端竞争；
- GPU kernel调度开销；
- 内存与文件I/O压力；
- 多进程同时加载checkpoint造成启动抖动。

新机器应扫描`1/2/4/8 workers`，记录总耗时、GPU利用率、CPU利用率和失败率，再选择稳定配置。

## 5. 分片、恢复与合并

### 5.1 分片设计

每个分片必须记录：

- `episode_start`；
- `n_trajectories`；
- `seed`；
- checkpoint的实际路径或hash；
- 模型结构和推理步数；
- 评估代码版本。

分片目录不要共享输出文件名。推荐：

```text
eval480/shards/worker_0/
eval480/shards/worker_1/
eval480/shards/worker_2/
eval480/shards/worker_3/
```

### 5.2 中断恢复

长评估中断时，不应重跑已完成的全部轨迹。正确流程：

1. 检查已完成分片及其episode范围；
2. 验证每个分片的轨迹数和文件完整性；
3. 只恢复缺失区间；
4. 用相同seed、模型和协议合并；
5. 检查区间无重叠、无缺口。

如果旧评估器只在进程结束时保存整个分片，恢复粒度就是一个worker。后续可进一步改为每若干条轨迹原子保存进度。

### 5.3 合并指标

本项目的模式指标定义：

- `SR = 成功轨迹数 / 总轨迹数`；
- `Coverage = 成功轨迹中出现的不同模式数`，Avoiding最大24；
- `H = -Σ p(m) log p(m) / log(24)`，只在成功轨迹上计算。

低SR模型的高条件熵不能单独解释为更好；必须联合报告`SR / Coverage / H`。

轨迹图统一用蓝色表示成功、红色表示失败，标题包含三项指标，便于快速发现“高成功率但单模式”的异常。

## 6. 分层评估协议

为了节约GPU时间并维持结论可信度，采用三级协议：

1. `Standard-120`：快速筛选、排除明显失败配置；
2. `Standard-480`：候选方法的严格闭环确认；
3. `Paired-1000 + JS + 多seed`：论文级分布比较。

经验：

- Standard-120可能漏掉低频模式，不能据此确认1–2个模式的细微差异；
- 120与480的覆盖排序可能改变；
- 相同episode和噪声的paired评估比两个独立采样集合更适合比较蒸馏前后的模式迁移；
- 单seed适合开发，不足以支持“方法普遍更优”的结论；
- 多seed应报告均值、离散程度和每个seed原始值，避免均值掩盖collapse。

任何候选都应与同checkpoint、同推理步数的solver-only或阶段入口进行配对比较，避免把Repair改善误归因于CTM。

## 7. 后台运行与断线保护

### 7.1 推荐tmux

交互节点内的长任务使用tmux：

```bash
tmux new-session -d -s experiment_name \
  'cd /absolute/path/to/repo && bash scripts/run_experiment.sh'
tmux ls
tmux capture-pane -pt experiment_name -S -100
```

SSH或聊天窗口断开不会终止tmux中的进程，但以下情况仍会终止任务：

- Slurm allocation到期或被取消；
- 节点重启；
- 任务触发OOM；
- tmux所在的作业cgroup被清理。

因此tmux是“终端断线保护”，不是“计算资源续期”。

### 7.2 脚本自包含

后台脚本不能依赖当前交互shell的隐式状态。应显式设置：

- 工作目录；
- Python解释器或环境激活；
- `CUDA_VISIBLE_DEVICES`；
- 输入checkpoint、buffer和输出目录；
- seed、结构、步数与训练预算。

使用：

```bash
set -euo pipefail
python -u ...
```

`-u`保证日志及时刷新；训练进程退出后再启动评估，使用`wait`检查子进程退出码。

### 7.3 状态与进度

训练日志应周期性打印：

- epoch/总epoch；
- loss分项；
- 当前学习率；
- 已用时间与预计剩余时间；
- checkpoint保存事件。

评估日志应打印：

- 已完成轨迹数/总数；
- 当前成功数；
- 最近更新时间。

不要仅凭GPU利用率判断任务是否卡死；应结合进程、日志更新时间、输出文件增长和显存占用。

## 8. Checkpoint管理与训练续跑

### 8.1 明确checkpoint语义

本项目中存在不同“best”：

- `structure_best_flow.pth`：结构迁移或Repair阶段按对应目标保存；
- `eval_best_flow.pth`：评估器默认加载的部署checkpoint；
- epoch checkpoint：用于绘制训练过程中的SR—覆盖—熵Pareto曲线。

如果评估器固定读取`eval_best_flow.pth`，必须显式复制或链接目标checkpoint，并在日志中记录来源。不能因为文件名叫“best”就假设它是闭环指标最优。

### 8.2 初始化验收

checkpoint初始化实验应保存并验证：

- 初始化方法：Random、Teacher、Full-student、PCA、Activation等；
- 实际加载路径；
- 加载覆盖率、missing/unexpected keys；
- 同结构直接加载时，逐参数最大绝对差应为0；
- student结构、参数量、推理步数。

旧实验曾因代码显式构造student而意外使用Random-init，导致错误归因。以后不能仅依据配置名判断初始化是否生效，必须从运行元数据和参数差异验证。

### 8.3 续训不一定是同一训练轨迹

若只恢复模型权重，没有恢复optimizer、scheduler和全局step，则属于：

> checkpoint续训 + optimizer/学习率重启

不能称为无缝延长训练。比较不同epoch时，应注明：

- optimizer状态是否恢复；
- 学习率是否重启；
- scheduler总周期是否变化；
- 数据顺序是否连续。

训练轮数增加也不能只比较终点。模式覆盖和SR可能沿Pareto前沿非单调变化，必须保存中间checkpoint并做闭环扫描。

## 9. 阶段隔离与数据依赖审计

每个实验必须区分：

1. **Initialization**：只构造初始权重；
2. **Repair**：保持原推理步数，恢复结构迁移后的功能；
3. **CD/CTM/Distillation**：减少推理步数；
4. **Evaluation**：闭环衡量SR和多模态性。

不能用Repair后的高SR证明“纯初始化很好”，也不能把CTM造成的模式损失归因于student容量。

同时明确数据假设：

| 路线 | 是否直接访问原始示范 | 是否间接含原始数据先验 |
|---|---:|---:|
| Full-student完整训练 | 是 | 是 |
| Full-student warm-start后蒸馏 | 蒸馏阶段通常否 | 是，来自初始化checkpoint |
| Teacher rollout buffer Repair | 否 | 仅通过teacher信号 |
| Teacher-only CD/CTM | 否 | 仅通过teacher与初始化 |

因此Full-student warm start不是严格的data-free蒸馏，即使蒸馏loss阶段没有重新读取原始数据。

生成teacher rollout buffer时，要记录采样seed、episode范围、teacher checkpoint、成功率、覆盖和熵。buffer本身的模式分布会限制后续Repair能够观察到的模式。

## 10. 多卡实验的公平性清单

四张GPU同时跑四个方法时，除目标变量外应固定：

- teacher、student结构与初始化checkpoint；
- rollout buffer或训练数据；
- seed及batch顺序；
- epoch、每epoch batch数、batch size；
- optimizer、学习率与scheduler；
- 推理步数；
- Standard评估的episode范围和seed；
- 评估worker数。

建议每个实验臂在启动时将完整命令写入日志或`config.json`。若不同方法单步计算成本不同，应同时报告wall-clock和训练step，而不能只比较“都训练500 epochs”。

训练完成后按同一顺序自动执行：

```text
checkpoint存在性检查
→ 配置/初始化断言
→ Standard-120
→ 指标门槛筛选
→ Standard-480
→ Paired-1000与多seed
```

## 11. 常见失败模式与对应措施

| 失败模式 | 表现 | 措施 |
|---|---|---|
| GPU申请与可见数量不一致 | 脚本部分任务未启动 | 启动前检查`nvidia-smi`并拒绝静默降级 |
| 终端断开导致任务停止 | 日志突然中断 | 在allocation内使用tmux；写独立启动脚本 |
| 单进程闭环评估过慢 | 显存和GPU利用率低 | 单GPU四worker分片，先验证逐轨迹等价性 |
| 直接平均分片熵/覆盖 | 汇总指标错误 | 合并原始success/mode后重新计算 |
| 分片seed错误 | 并行与串行结果不同 | 用全局episode index派生随机性 |
| 初始化未真正加载 | 数据反常、错误归因 | 保存加载路径并断言参数差异 |
| “续训”未恢复optimizer | 曲线不可直接拼接 | 标注学习率重启，避免称为连续训练 |
| 只看训练loss选checkpoint | SR或多样性退化 | 保存中间点，联合SR/Coverage/H选择 |
| Standard-120过度解读 | 低频模式缺失 | 候选补Standard-480和多seed |
| 训练、Repair和CTM混为一谈 | 无法定位collapse | 每阶段独立评估同一checkpoint |
| 数据假设描述不清 | data-free结论不成立 | 区分直接访问与checkpoint中的间接先验 |
| 硬编码绝对路径 | 换空间后无法运行 | 使用项目根目录、环境变量或命令行参数 |

## 12. 迁移到新工作空间的最小Runbook

1. 安装环境并固定Python、CUDA和依赖版本；
2. 检查数据、checkpoint和bundle路径，不把大文件提交Git；
3. 将运行脚本中的绝对路径改为参数或环境变量；
4. 用一个小checkpoint完成单条推理smoke test；
5. 用固定16条轨迹验证单worker与四worker完全等价；
6. 检查分片合并后的轨迹数、episode范围和指标；
7. 启动一个短训练，验证checkpoint、日志和`STATUS`均会生成；
8. 再启动多GPU实验矩阵，并确保一GPU一实验臂；
9. Standard-120筛选后再投入Standard-480；
10. 最终候选补Paired-1000、JS和多seed；
11. 将实验命令、代码版本、数据依赖和结果同步写入文档。

# 默认Rollout与评估并行协议

后续Teacher/Student rollout及Standard-120/480评估，启动前先检查可用GPU数量、
显存和Slurm CPU核数。默认采用：

```text
每个模型占用1张GPU
每张GPU启动4个worker
OMP_NUM_THREADS=1
MKL_NUM_THREADS=1
OPENBLAS_NUM_THREADS=1
```

episode区间必须互不重叠，完成后统一合并轨迹与指标。只有CPU核数不足、显存不足、
环境不支持多进程或实测吞吐下降时才减少worker，并在STATUS/metadata中记录实际
GPU数和workers-per-GPU。不要仅根据显存空闲继续增加worker；当前4卡节点只有
20个CPU核，`4 worker/GPU`共16个进程已接近整机吞吐上限。
